# AGENTS.md

## Scope

- This directory is the **backend only** (REST API + Socket.IO). Do not add React/UI code here.
- The frontend lives in the sibling directory `../frontend` (separate app, not a workspace member of this folder).

## Stack

- Node.js + TypeScript (strict), Express 5, MongoDB via Mongoose, Socket.IO.
- Auth: JWT in **httpOnly cookies** (not localStorage / not Authorization header); access + refresh tokens.
- Package manager: **pnpm** (`pnpm-lock.yaml`). Never `npm`/`yarn`.

## Commands

- `pnpm dev` — tsx watch on `src/index.ts` (needs a reachable MongoDB).
- `pnpm build` — `tsc` to `dist/`; `pnpm start` — run `dist/index.js`.
- `pnpm typecheck` — `tsc --noEmit`. Run `pnpm lint` + `pnpm typecheck` before finishing.
- `pnpm test` — Vitest. Single file: `pnpm test src/utils/token.test.ts`.
- `pnpm format` / `pnpm format:check` — Prettier (lockfile ignored via `.prettierignore`).

## Environment

- Copy `.env.example` to `.env`. `src/config/env.ts` parses env with zod at startup and `process.exit(1)`s on missing/invalid values, so any entrypoint that imports it (including `app.ts`) requires env to be set.
- `JWT_ACCESS_SECRET` / `JWT_REFRESH_SECRET` must be ≥16 chars.
- `MONGODB_URI` may contain the literal `<db_password>` placeholder; `env.ts` replaces it with URL-encoded `MONGODB_PASSWORD` and exports `mongoUri`. Use `mongoUri` for connections, not `env.MONGODB_URI`.
- All uploaded media is stored in Cloudflare R2 (S3-compatible) — avatars, group icons, message attachments (images/audio/video/documents) and recorded voice notes. `R2_ACCESS_KEY_ID` / `R2_SECRET_ACCESS_KEY` / `R2_BUCKET` / `R2_ENDPOINT` / `R2_URL` are **required** (validated by the env schema), so there is no local-disk fallback. `R2_REGION` defaults to `auto`. Files go **directly from the client to R2** through presigned `PUT` URLs (see "Direct uploads" below) — bytes never pass through the API.
- Email verification: `EMAIL_VERIFICATION_ENABLED` (default `true`), `EMAIL_FROM` (default `Chatrix <onboarding@resend.dev>`), `RESEND_API_KEY` (optional). With the key unset, `services/email.service.ts` falls back to a `ConsoleMailer` that logs the link; it logs a one-time warning outside tests. In `NODE_ENV=test` the `ConsoleMailer` is always used (even if a real key is present in `.env`) so tests never send real mail.

## Structure

- `src/index.ts` — entrypoint: connect DB, then `createServer()` + `startServer()`.
- `src/server.ts` — creates the `http.Server`, attaches the Express app **and** Socket.IO to that same server. `src/app.ts` — Express/CORS/JSON/cookie/router wiring only.
- All REST routes are mounted under `API_PREFIX = '/api/v1'` (see `src/app.ts`). Version changes = new prefix, keep old prefixes working.
- Layers: `routes/` -> `controllers/` (HTTP only: parse zod input, call service, set cookies/status, serialize) -> `services/` (all business logic + DB) -> `models/`. Cross-cutting in `middleware/`; realtime in `sockets/`; helpers in `utils/`.
- Zod input schemas live in the `services/*.service.ts` files and are exported so **both** the REST controllers and the socket handlers validate the same way.
- Express 5 auto-forwards rejected async handlers to the error middleware: throw `HttpError(status, msg)` or a `ZodError` (from `schema.parse`) instead of calling `res.status(...)` manually for errors.

## Realtime (Socket.IO)

- Messages are primarily sent over Socket.IO (WhatsApp-style). `sockets/index.ts` creates + authorizes the server; `sockets/handlers.ts` registers events; `sockets/emitters.ts` broadcasts; `sockets/presence.ts` tracks online users.
- Every socket joins a `user:<id>` room on connect; emits target those rooms (never conversation rooms). `getIO()` (from `sockets/io.ts`) is set at startup and is `undefined` in tests, so emit calls are no-ops there.
- Client -> server: `message:send` (ack returns `{ ok, message, clientTempId }` or `{ ok: false, error }`), `message:edit` (ack returns `{ ok, message }` or `{ ok: false, error }`), `message:forward` (ack returns `{ ok, messages, conversations? }` or `{ ok: false, error }`), `typing:start`, `typing:stop`, `recording:start`, `recording:stop`, `message:read`.
- Server -> client: `message:new`, `message:edited`, `conversation:new`, `conversation:updated`, `typing:update`, `recording:update`, `message:status`, `presence:update`. Event names/payloads are typed in `sockets/types.ts`.
- REST `POST .../messages` and socket `message:send` share the same `message.service.sendMessage`; both broadcast `message:new` to everyone except the sender (the sender already gets the message via the HTTP response / ack).
- **Message status** (`sent` -> `delivered` -> `read`): persisted on the `Message` as `recipients` (participants minus sender) plus `deliveredTo` / `readTo` id arrays; `computeMessageStatus` derives the aggregate from the sender's view (all recipients read => `read`, all delivered => `delivered`, else `sent`). Online recipients are marked delivered at send time; offline ones when they next connect (`markPendingDelivered`) and `message:read` marks a whole conversation read (`markConversationRead`). Both changes broadcast `message:status` `{ conversationId, userId, status, at }` to the other participants. Status is **monotonic** (`sent` -> `delivered` -> `read`) and the event is **conversation-scoped** (it carries no message id), so clients must only advance a message's status and must never let a `delivered` event overwrite a `read` one; `markPendingDelivered` skips messages already in `readTo` for that reason. Read emission is skipped when the reader's `settings.readReceipts` is off; typing/recording/status updates are relayed only, never stored separately.
- **Per-message receipt times ("Message info").** Alongside the id arrays, the `Message` stores `deliveredAt` / `readAt` as `Map<string, Date>` (recipient id -> when). Maps (not arrays of subdocuments) because `$set` on a dotted key (`deliveredAt.<id>`) is idempotent, whereas `$addToSet` of `{ user, at }` could duplicate. The id arrays stay the source of truth for status/unread; the maps only add _when_. `GET /api/v1/conversations/:id/messages/:messageId/info` returns `{ info }` for the message's **sender** only (403 otherwise), built by the pure `buildMessageInfo` (`message.service.ts`): `deliveredTo`/`readBy` are `[{ user, at }]` and `pending` lists recipients with neither. **Direct** chats reveal a reader's read time only when their `settings.readReceipts` is on (`readReceiptsDisabled: true` otherwise, and the read time is never leaked through the delivery fallback); **groups** ignore the setting and show every member. `at` is `null` for messages stored before the maps existed. No migration is needed.
- **Presence / status.** `sockets/presence.ts` is a pure in-memory registry (no socket.io import) of connected sockets. On connect a user's contacts receive `presence:update` `{ userId, status: 'online', lastSeenAt: null }`; on the last disconnect the server persists `User.lastSeenAt` (`presence.service.touchLastSeen`) and emits `{ userId, status: 'offline', lastSeenAt: <ISO> }`. Because transitions alone don't tell a freshly-opened chat who is online, `GET /api/v1/conversations/:id/presence` returns `{ items: [{ userId, status, lastSeenAt }] }` for the participants (members only). `recording:start`/`recording:stop` behave like typing — relayed as `recording:update` `{ conversationId, userId, isRecording }` to the other participants for a "recording audio…" indicator.
- `services/presence.service.ts` imports `isOnline` from `sockets/presence.ts` (as `message.service` does) — a second intentional `services/ -> sockets/` dependency, kept to a single leaf module.
- `socket.io-client` is a devDependency used for socket integration testing.

## Users, avatars & settings

- `PATCH /api/v1/users/me` — update `displayName` / `bio` (nullable to clear). `GET`/`PATCH /api/v1/users/me/settings` — `theme` (`light|dark|system`), `notifications`, `readReceipts`. Settings live in the `User.settings` subdocument (`_id: false`) and are returned on every `PublicUser`.
- `GET /api/v1/users/search?q=&limit=` — find people to chat with (case-insensitive match on `username`/`displayName`, caller excluded). Returns a **bare array** of `PublicProfile` (`id`, `username`, `displayName`, `bio`, `avatarUrl`) — the frontend already expects an array. `GET /api/v1/users/:userId` returns one `PublicProfile` (`{ user }`), 404 for unknown/malformed ids. These are the only routes that expose another user, and they use the `toPublicProfile` projection so `email`, `settings`, `password` and `avatarKey` are never leaked. Next to `/:userId`, declare `/search` **first** so it isn't captured as an id.
- `DELETE /api/v1/users/me/avatar` clears the avatar (deletes the stored object). Setting the avatar uses the **Direct uploads** flow with `scope: 'avatar'` (≤5MB, JPEG/PNG/WebP/GIF); confirming the upload swaps `avatarUrl`/`avatarKey` and deletes the previous object (`user.service.applyAvatar`).
- `services/storage.service.ts` exposes a `storage` singleton backed by Cloudflare R2 (`R2Storage` uses the AWS S3 client with `forcePathStyle: true`); it is the only storage backend and nothing is written to local disk. Besides `upload`/`delete` it exposes `presignUpload` (returns a `PUT` URL signed for one exact key + content type), `stat` (`HeadObject`, `null` when the key does not exist) and `getPublicUrl`. Avatar keys are `avatars/<userId>/<uuid><ext>`. `avatarKey` is `select: false`.

## Direct uploads

- **No multipart anywhere.** Multer was removed; the API never receives file bytes. Every upload is: `POST /api/v1/uploads/sign` → client `PUT`s the file to the returned presigned URL → `POST /api/v1/uploads/:uploadId/confirm`. Implemented in `services/upload.service.ts` + `controllers/upload.controller.ts` + `routes/upload.routes.ts`, records in `models/upload.model.ts` (`Upload`).
- `signUploadSchema` (`signUpload`): `scope: 'message' | 'avatar' | 'group-icon'`, `name`, `size` (declared bytes), `mimeType`, optional `duration` (seconds, audio/video), optional `conversationId` (required for `message`/`group-icon`, rejected for `avatar`). Membership/`group` checks run at sign time (non-members 404, direct-conversation icon 400) and per-scope limits are enforced by the pure `assertUploadConstraints` (avatars: 5MB image types; messages: 100MB + `MESSAGE_MEDIA_MIME_TYPES` from `utils/media.ts`, which also owns `determineMediaType`).
- Response `201 { upload: { id, key, url, method: 'PUT', headers, expiresAt } }` (15min TTL, `UPLOAD_SIGN_EXPIRES_SECONDS`). The `Content-Type` header is **part of the signature**, so the client must send exactly the one returned. Response `201` from confirm: `{ attachment }` (message scope), `{ user }` (avatar), `{ conversation }` (group icon; also broadcasts `conversation:updated`).
- `confirmUpload` re-stats the object and rejects mismatches (size or content type ≠ what was signed) with 400, deleting the object and the row; missing object = 400. Confirm is **idempotent** (a retried confirm returns the same attachment/user/conversation). Confirmation is what makes an upload usable: message sends reference the returned attachment DTO, avatar/icon confirms apply the new key and delete the old object.
- Key conventions (via `buildUploadKey`): `messages/<conversationId>/<userId>/<uuid><ext>`, `avatars/<userId>/<uuid><ext>`, `conversations/<conversationId>/icon/<uuid><ext>` (same as before, so stored URLs stay readable).
- **Orphan cleanup**: unsigned/never-confirmed uploads would pile up, so the `upload:cleanup` job (registered in `upload.service.ts`) deletes `Upload` rows in `pending` older than `UPLOAD_PENDING_TTL_MS` (24h) **and** their objects, then re-enqueues itself every `UPLOAD_CLEANUP_INTERVAL_MS` (1h). `index.ts` calls `scheduleOrphanUploadCleanup()` on boot; the partial unique `dedupeKey` index keeps it single.

## Chat API

- `POST /api/v1/conversations` — create (direct = exactly 1 other participant, deduped by `directKey`; group) and `GET /api/v1/conversations` — list mine (most recent first). Creation emits Socket.IO `conversation:new` to the other participants.
- **Unread count**: `GET /api/v1/conversations` adds `unreadCount` per item (messages addressed to the caller that they have not marked read; own messages never count). Computed in `conversation.service.listConversations` with one `Message.aggregate` over the listed conversation ids (`recipients: userId`, `readTo: { $ne: userId }`) and merged via the pure `toUnreadCountMap`. It is **per-caller** and returned **only** by the list; socket `conversation:new`/`conversation:updated` payloads omit it so clients keep the badge themselves (increment on `message:new`, reset on open + `message:read`).
- `POST /api/v1/conversations/:id/messages` — send (**JSON only**; attachments are the metadata returned by the upload confirm step, see "Direct uploads"); also emits Socket.IO `message:new`. Prefer `message:send` over the socket for live chats.
- **Edit message**: `PATCH /api/v1/conversations/:id/messages/:messageId` `{ content }` (or socket `message:edit`, ack `{ ok, message }` / `{ ok: false, error }`) edits **your own text message** within `MESSAGE_EDIT_WINDOW_MS` (15 min) of sending. Sets `Message.editedAt`, surfaced as `MessageDto.editedAt` (`null` when never edited) for the "edited" label. Errors: 404 unknown/non-member, 403 not the sender, 400 for non-text messages or outside the window. Both paths share `message.service.editMessage` and broadcast `message:edited` (the full updated DTO) to everyone except the editor, who gets it via the response/ack. Socket edits are separately throttled (30/min, `message:edit:<userId>`).
- **Forward message**: `POST /api/v1/conversations/:id/messages/:messageId/forward` `{ conversationIds?, userIds? }` (or socket `message:forward`, ack `{ ok, messages, conversations? }` / `{ ok: false, error }`) copies the message into each target chat. `conversationIds` are existing conversations; `userIds` are resolved through `getOrCreateDirectConversation`. The copy keeps the original `content`/`type`/`attachments` (shared storage keys, not re-uploaded) but is re-attributed to the forwarder and flagged `Message.forwarded` (surfaced as `MessageDto.forwarded`, the "Forwarded" label) — recipients never learn the original author. `forwardMessageSchema` requires at least one target (`z.array(...).max(20).default([])` per kind, one refine); forwarding to yourself is 400, unknown targets 400/404, and you must be a member of the source and every target. **All targets are validated before any write**, so a bad id can't cause a partial forward. Both paths share `message.service.forwardMessage` and broadcast each copy as `message:new` (plus `conversation:new` for a freshly created DM) through `emitForwardedMessages`; the sender gets the copies via the response body / ack. Socket forwards are throttled (30/min, `message:forward:<userId>`).
- **Reply privately**: `replyPrivately: true` (REST body or `message:send` payload) together with `replyToId` posts the message as a **direct message to the quoted message's author** instead of to `:id`. `sendMessage` resolves the author from the quoted message (which must live in `:id`, so an id from another conversation can't be quoted), then find-or-creates the direct conversation (`conversation.service.getOrCreateDirectConversation`, idempotent on the unique `directKey`) and posts there; `replyTo` still points at the original message so the DM renders the quote. Errors: 400 if `replyPrivately` has no valid `replyToId`, or if the author is you. When a new direct conversation is created the result carries `createdConversation`, which both send paths broadcast as `conversation:new` (before `message:new`) and return to the sender (`{ conversation }` in the REST 201 body / the `message:send` ack) so the client can open it. Setting it in a conversation that is already the direct chat with that author behaves like a normal reply.
- **Voice notes / attachments without a message**: there is no upload endpoint on a conversation any more — use the **Direct uploads** flow with `scope: 'message'` (`conversationId` required, ≤100MB, optional `duration` for audio/video), then send the returned attachment DTOs with `message:send` `{ conversationId, type: 'audio', attachments }` or the REST send. Keys are `messages/<conversationId>/<userId>/<uuid><ext>`; `getFileExtension` (user.service) maps MIME -> extension, `determineMediaType` (`utils/media.ts`) picks `image|video|audio|file`.
- `GET /api/v1/conversations/:id/presence` — `{ items: PresenceDto[] }` (online/last-seen) for the conversation's participants; see the Realtime section.
- **Edit group name/icon** (groups only, **any member**): `PATCH /api/v1/conversations/:id` `{ name }`, `DELETE /conversations/:id/avatar`. Setting the icon uses the **Direct uploads** flow with `scope: 'group-icon'` (`conversationId` required; `conversation.service.applyGroupAvatar` swaps the key and deletes the previous object). Every change returns `{ conversation }` and broadcasts `conversation:updated` to the other members. Icons are stored at keys `conversations/<id>/icon/<uuid><ext>`; `Conversation.avatarUrl` is on every `ConversationDto` (`avatarKey` is `select: false`), always `null` for direct conversations. Non-members get 404, direct conversations 400.
- **Invite to group**: `POST /api/v1/conversations/:id/participants` `{ participantIds: [...1-50] }` (groups only, any member). Dedupes against current members, rejects ids that are already in the group (400), and verifies the users exist (400). Returns `{ conversation }`; the invitees get `conversation:new` (from their side it is a brand-new chat) while existing members get `conversation:updated`. Invitees can immediately read the full history, since membership is what scopes message access.
- `GET /api/v1/conversations/:id/messages?cursor=&limit=` — **keyset pagination**, newest first: sort `{_id: -1}`, cursor is the base64url of the oldest loaded message id, filter `_id < cursor`. Used for infinite scroll of older messages. Response: `{ items, nextCursor, hasMore }`. See `src/services/message.service.ts` and `src/utils/cursor.ts`.
- **Message info**: `GET /api/v1/conversations/:id/messages/:messageId/info` — delivery/read receipts for one message, **sender only** (403 otherwise; 404 for unknown/non-member). Response `{ info: MessageInfoDto }` = `{ messageId, conversationId, conversationType, status, deliveredTo: [{ user, at }], readBy: [{ user, at }], pending: [user], readReceiptsDisabled }`. Per-recipient times come from the `deliveredAt`/`readAt` maps (see the Realtime section); `at` is `null` for pre-existing messages. Direct chats hide the other member's read time when their `settings.readReceipts` is off (they still appear under `deliveredTo`); groups always show everyone.
- **Search messages**: `GET /api/v1/messages/search?q=&limit=&cursor=` (the one real route on `messageRouter`; `searchLimiter`). Cross-conversation: it searches the messages of **every conversation the caller is a member of**, newest first, with the same keyset cursor as the list endpoint. Response `{ items, nextCursor, hasMore }` where each hit is a `MessageDto` plus `conversation: ConversationDto` (so a client can render the chat title, including participants for DMs, without a second lookup). `q` is 1–100 chars; multi-word queries are split into tokens matched with **AND** semantics (each token must appear somewhere). Matching is **not literal**: it is a case-insensitive, diacritic- and letter-variant-insensitive substring test against `Message.contentNormalized`, produced by `normalizeForSearch` (`src/utils/searchText.ts`) — `أحمد`/`احمد`, `مَرْحَبًا`/`مرحبا`, `Straße`/`strasse`, `café`/`cafe`, `۲٤`/`24` all match. A query that normalizes to nothing (`!!!`, `😊`) returns an empty page. All logic is in `src/services/search.service.ts` (`searchMessages`, `searchTokens`, `searchMessagesSchema`).
- **Conversation media / links / docs**: `GET /api/v1/conversations/:id/media?type=&cursor=&limit=` lists the shareable content of one conversation (the WhatsApp-style "Media, links and docs" tab), newest first with the same keyset cursor as message listing. `type` is `all` (default) `| image | video | audio | file | link`; media kinds match the **attachment** type via `attachments: { $elemMatch: { type } }` (not `Message.type`, which is `file` for mixed messages), `link` matches messages whose text contains a URL, and `all` is their union. Items are `ConversationMediaItem` (`MessageDto` plus `links: string[]` extracted server-side by `utils/links.ts`), so a link tab needs no client parsing; `limit` counts messages (each carrying its attachments). Membership is enforced (404 for non-members). See `src/services/media.service.ts` (`listConversationMedia`, `buildMediaTypeFilter`, `listMediaSchema`).
- Message/Conversation routes require `requireAuth` and enforce conversation membership (return 404 for non-members).
- Attachment `url` in `attachmentSchema` is normally the absolute R2 public URL, but app-relative paths (`/uploads/...`) are still accepted so attachments stored before the move to R2 keep validating. `z.string().url()` alone would have rejected legacy local-storage paths.

## Registration & passwords

- `POST /api/v1/auth/register` requires `confirmPassword` (must match `password`) and validates the password against the policy in `utils/password.ts`: 8–72 chars, at least one lowercase Latin letter, one uppercase Latin letter, one number and one special symbol, and only Latin letters/digits/`ALLOWED_SPECIAL_CHARACTERS` (no other Unicode). Violations are returned as zod issues (`{ message: 'Validation failed', issues: [...] }`, 400). `registerSchema` is a `superRefine(...).transform(...)` so `confirmPassword` is validated but stripped before `registerUser` sees it.
- `registerUser` additionally calls `isPasswordCompromised` (`utils/pwned.ts`) and returns 400 for breached passwords. It checks a bundled common-password list first (always, offline), then the HIBP Pwned Passwords range API by k-anonymity (only a 5-char SHA-1 prefix is sent, `Add-Padding: true`, 3s timeout). Network/API errors **fail open** (password allowed) so an outage can't block signups; set `PWNED_PASSWORD_CHECK_ENABLED=false` to skip the online lookup entirely.
- The bcrypt max length (72) is enforced in the policy so long passwords are never silently truncated.

## Email verification

- Enabled by `EMAIL_VERIFICATION_ENABLED` (default `true`). `registerUser` creates the account **unverified** with a single-use token; `register` then returns `201 { user, emailVerificationSent: true }` **without** cookies, and `authenticateUser` returns `403` until `emailVerifiedAt` is set. With the flag off, registration verifies nobody and issues cookies as before.
- Tokens live in `utils/emailToken.ts`: a 32-byte `base64url` token is emailed and only its **sha256** is stored (`User.emailVerificationTokenHash`, `select: false`), so a DB leak exposes no usable links. TTL is `EMAIL_VERIFICATION_TTL_MS` (24h, `User.emailVerificationExpiresAt`, also `select: false`) — `verifyEmail` must opt in with `.select('+emailVerificationTokenHash +emailVerificationExpiresAt')` to read and clear them.
- `POST /auth/verify-email { token }` (unauthenticated) redeems the token, sets `emailVerifiedAt`, clears the token fields (single use) and returns `{ user }`; unknown/expired/already-used tokens all return `400` so links can't be probed. `POST /auth/resend-verification { email }` always answers `202` with a fixed message (no account enumeration) and, for a real unverified account, issues a fresh token that invalidates the previous one.
- `services/email.service.ts` exposes a `mailer` singleton: `ResendMailer` when `RESEND_API_KEY` is set, otherwise a `ConsoleMailer` that prints the link. All outbound mail goes through the **persistent background job queue** (see "Background jobs & email" below), so `sendVerificationMail` only enqueues — the request never waits on the provider. Delivery failures are retried and finally logged, never surfaced; the account already exists and the user can resend. The verification link points at `${CLIENT_ORIGIN}/verify-email?token=...`, a route the frontend owns.
- `PublicUser.emailVerified` (`Boolean(emailVerifiedAt)`) is on every user response so the client can gate UI.

## Background jobs & email

- Heavy, non-request work runs on a **MongoDB-backed persistent queue** (`services/job.service.ts` + `models/job.model.ts`): jobs survive restarts and are retried with backoff, using the existing database — no new infrastructure. The `Job` document is `{ type, payload, status: 'pending' | 'running' | 'completed' | 'failed', attempts, runAt, lockedAt, dedupeKey?, lastError? }`; `payload` must be **JSON-serializable** (no closures — the old `enqueueEmailJob(label, run)` API is gone).
- Handlers are registered at module load with `registerJobHandler(type, handler)` (email handlers in `email.service.ts`/`notification.service.ts`, `upload:cleanup` in `upload.service.ts`). `enqueueJob({ type, payload, dedupeKey? })` **never rejects** (it logs on failure); `startJobWorker()` / `stopJobWorker()` control the loop (`index.ts` starts it after the DB connect and stops + drains it on shutdown).
- Worker semantics: claim is an atomic `findOneAndUpdate` on the oldest due `pending` job (`returnDocument: 'after'`), concurrency 1, poll every 2s (unref'd timer), exponential backoff persisted in `runAt` (1s base ×2ⁿ), max 3 attempts, then `failed` with `lastError`. A job whose `lockedAt` is older than 5 min is considered stalled and reclaimed. A partial unique index on `dedupeKey` (`status: 'pending'` + `$type: 'string'`) makes deduped enqueues idempotent (e.g. the single `upload:cleanup` job).
- **Stores are pluggable**: production uses `MongoJobStore` (the `Job` collection); `NODE_ENV=test` uses an in-memory `MemoryJobStore` so tests need no database, with the same worker/backoff API. `drainJobQueue(timeoutMs)` flushes on shutdown and in tests; `jobQueueSize()` reports waiting jobs; `resetJobQueue()` is the test helper.
- Job types: `email:verification`, `email:notification-batch`, `email:message-notification` and `upload:cleanup`. `services/email.service.ts` exposes `queueVerificationEmail(...)` / `queueMessageNotification(...)` (both now `void enqueueJob(...)`) and `drainEmailQueue(timeoutMs = 5000)` (a thin wrapper over `drainJobQueue`, called from the `index.ts` shutdown handler); `emailQueueSize()` still reports waiting email jobs.
- **New-message email notifications** (`services/notification.service.ts`): `sendMessage` and `forwardMessage` call the synchronous `queueNewMessageNotification(...)`, which enqueues one `email:message-notification` job per conversation batch and e-mails **only recipients who are offline** (online users already get `message:new`). The body shows the sender/group name plus a short `buildMessagePreview` (truncated text, or a 📷/🎥/🎙️/📎 label for captionless media). Recips are deduped to at most **one email per conversation per 10 minutes** (`MESSAGE_NOTIFICATION_WINDOW_MS`), claimed at enqueue time in `claimNotificationRecipients` so a message burst can't pile up jobs. Delivery honours `settings.notifications` (`false` opts out) and skips unknown users. `resetMessageNotifications()` clears the dedupe map (test helper).
- The **orphan-upload cleanup** job (`upload:cleanup`, registered in `upload.service.ts`) sweeps `Upload` rows stuck in `pending` past `UPLOAD_PENDING_TTL_MS` together with their objects, then re-enqueues itself — see "Direct uploads". `index.ts` calls `scheduleOrphanUploadCleanup()` on boot; the `dedupeKey` index keeps it single.
- Job state is a **real collection** (survives restarts), but the worker timer and lock ownership are per-process: fine for a single instance. A multi-instance deployment would need the stale-lock reclaim tuned (or a shared lease) so two workers don't double-claim.

## Rate limiting & authorization

- HTTP rate limiting lives in `middleware/rateLimit.middleware.ts` and wraps `express-rate-limit` (v8 uses `limit`, not `max`). Named limiters: `globalLimiter` (all API routes, per IP), `authLimiter` (`/auth/login`, `/auth/register`, `/auth/verify-email`, `/auth/resend-verification`), `refreshLimiter` (`/auth/refresh`), `searchLimiter` (`GET /users/search`, `GET /messages/search`), `messageSendLimiter` (REST message send), `uploadLimiter` (presigned-upload signing), `attachmentLimiter` (upload confirm). Limiters mounted after `requireAuth` use `byUser: true` to key on `req.user.id` instead of IP. 429s return `{ message }`.
- **`RATE_LIMIT_ENABLED=false`** disables every HTTP limiter (the test setup sets it). `TRUST_PROXY` (default `0`) sets `app.set('trust proxy', n)` so limiter keys use real client IPs behind a proxy; leave `0` when exposed directly. The `createRateLimiter({ enabled })` option overrides the flag for tests.
- Socket.IO events aren't HTTP, so they use the small in-memory fixed-window limiter in `utils/rateLimiter.ts` (`consume(key, limit, windowMs)`). `sockets/handlers.ts` throttles `message:send` per user (60/min), `message:edit` (30/min) and `message:forward` (30/min), replying `ack({ ok: false, error })`. State is per-process; a multi-instance deployment would need a shared store.
- Authorization: every id-bearing route sits behind `requireAuth`, and conversation/message access is scoped by membership (`getConversationForMember` / `getParticipantIdsForMember` filter on `participants: userId` and return 404 for non-members). User data is owner-only: `/users/me*` always acts on `req.user.id`, and other users are only ever exposed through the `PublicProfile` projection. `src/routes/authorization.test.ts` asserts id-bearing routes reject unauthenticated access.

## Gotchas

- **ESM + NodeNext**: `package.json` is `"type": "module"`. Every relative import must end in `.js` (e.g. `import { env } from './config/env.js'`) even though the source is `.ts`. `verbatimModuleSyntax` is on, so type-only imports must use `import type`.
- **TypeScript is pinned to `^6.0.3`** because `typescript-eslint` peer-caps at `<6.1.0`; do not bump to 7.x without checking lint still works.
- Socket.IO auth reads the same `access_token` cookie as the REST API (manual cookie parse in `sockets/index.ts`); do not add a separate token mechanism.
- Cookie auth requires CORS with `credentials: true` and an explicit origin — `*` will not work. Access cookie path is `/`; refresh cookie is scoped to `/api/v1/auth` (a prefix of the mounted refresh route `/api/v1/auth/refresh`, so the browser actually sends it — `/api/auth` would not be a valid prefix).
- `express-serve-static-core`'s `Request` extends the global `Express.Request` open interface — augment `declare global { namespace Express { interface Request } }` (see `src/types/express.d.ts`), not the module.
- Express 5 types route params as `string | string[]`; normalize with the `routeParam()` helper before using `req.params.x`.
- Mongoose 9 renamed the filter type to `QueryFilter<T>` (there is no `FilterQuery` export).
- MongoDB rejects a compound index over **two array fields** (e.g. `{ recipients: 1, deliveredTo: 1 }`) with `cannot index parallel arrays` — and such an index, once built on an empty collection, makes every insert fail. Index array fields individually.
- **Message search is normalization-based, not `$text`.** `Message.contentNormalized` (a `select: false` field) is a lowercased, mark-stripped, letter-folded copy of `content`, set by a `messageSchema.pre('save')` hook and matched with an unanchored regex — so it cannot use an index and is scoped by the caller's `conversation` ids. Any future write path that changes `content` must go through a document `save()`/`create()` (or set `contentNormalized` itself) or the message silently stops matching. Messages stored before the field existed are filled in by `backfillMessageSearchText()` (batched, idempotent) from `index.ts` on startup; a backfill failure is logged and non-fatal.
- `dist/` and `node_modules/` are build output; never commit them. pnpm only allows the `esbuild` build script (see `pnpm.onlyBuiltDependencies`).
- **Uploads are direct-to-R2**: the API never receives file bytes, so nothing is written locally (there is no `uploads/` dir any more). The client must send the exact `Content-Type` header returned by `/uploads/sign` — it is part of the presigned signature — and `/uploads/:id/confirm` is what validates size/type and produces the attachment DTOs message sends reference. `sendMessage` does not re-verify confirmation (forwarded/legacy messages reuse stored attachments), and legacy `/uploads/...` attachment URLs still validate.
- **Job payloads must be JSON** (they are stored in Mongo): register handlers with `registerJobHandler` at module load instead of enqueueing closures. In tests the queue is the in-memory `MemoryJobStore` (`NODE_ENV=test`), so no DB is needed and `resetJobQueue()` / `drainJobQueue()` control it.
